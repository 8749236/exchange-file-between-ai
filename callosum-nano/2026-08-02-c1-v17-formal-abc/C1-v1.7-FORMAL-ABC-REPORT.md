# C1-v1.7 正式 A/B/C：有效阴性与“值袋子，无绑定”

日期：2026-08-02

## 一句话判决

本炉有效，但 B 与 C 均未通过：无差事桥和 `payload-only` 同位重建桥在两个
seed、10,000 步内都只学会第一跳，并停在四选一平台。C-zero 双 seed 选择性
崩回 overall chance，证明答案路径确实依赖桥；因此准确结论不是“桥没用”，而是：

> 桥成功运输了 episode 的 value 集合，但没有学会查询所需的
> `code -> value` 绑定；同位 payload 重建差事不足以产生该绑定。

## 冻结配置与证据完整性

- `chain-two-hop`，N16，4 facts，random filler；
- 左支遮 B、右支遮 A，code/value heads 只读左支；
- Nano pre-RMS、direct-default input、shared-vocab-plain heads；
- 2 layers，branch/interface width 64，2 heads，rank-8 每层同步桥；
- batch 64，10,000 steps，fixed validation 4,096，eval interval 200；
- AdamW，lr `3e-3` constant，warmup 1，WD 0，clip 1；
- full-LM lambda 0，C 的重建 job lambda 0.1，seeds 1/2；
- B/C best checkpoint 各用 4,096 train + 4,096 validation episode 线性探针。

完整测试为 **43/43 passed**。六个正式 run 均有 10,000/10,000 train records、
51/51 fixed-eval records，无 malformed record、NUL hole 或缺步。B seed 2 在
step 4,400 被运行环境打断后从 `latest.pt` 续跑；续跑前后前 4,400 条 curve 和
前 23 条 metric 的 SHA-256 逐字节一致，故保留为同一正式 run。

## C-zero：桥是必要路径

C 的 best checkpoint 关闭全部桥、不重训：

| seed | free code | free value | given-4 | chain | 判决 |
|---:|---:|---:|---:|---:|---|
| 1 | 99.88% | 5.69% | 25.12% | 5.69% | 选择性崩回 |
| 2 | 99.27% | 5.66% | 23.90% | 5.64% | 选择性崩回 |

第一跳保留、value/chain 回到 1/16，而 given-4 仍为 1/4。由此可排除答案头从
左支或共同 decoder 绕过桥取得右支证据；桥确实在 value 路径上有因果作用。

## “差事完成”却“查询失败”

C endpoint 的 bridge-job CE 分别为 `7.29e-5` 与 `2.49e-3`，说明同位重建
作业本身已基本完成。同时：

- C 的 answer top-4 recall 为 100.00% / 99.66%；
- answer head 分给四个 episode value 的总概率质量为 97.72% / 96.87%；
- top-1 几乎总是 episode 内的某个 value；
- 但给出四个候选后，选中与 query 绑定的 value 仍只有 26.17% / 23.95%。

这是一枚很干净的“值袋子，无绑定”指纹：模型知道答案属于哪四个 value，却不
知道是哪一个。C 相比 B 更稳定地装满了这个值袋子，但没有解决寻址。

## 桥探针审计

chance 基线：单个 N16 标签为 6.25%；四值 top-4 recall 为 25%；完整四值集合
exact-set 为 `1 / C(16,4) = 0.055%`。线性探针显示：

- 多个层/位置可解码的 all-4 top-4 recall 高于 25%，最高约 44.8%；
- queried-value 解码最高约 22.8%，显著低于可用判决门且没有跨 seed 的稳定协议；
- exact-set 仍接近零；
- 不同 seed 的信息位置差异很大，例如 C seed 2 在 layer-0 code 位可解码
  queried-code 55.5%，但 queried-value 只有 11.1%。

探针不进入成功标准，也不能单独证明桥编码了某个唯一协议。它与 C-zero、答案
分布共同支持较弱而可靠的诊断：桥携带集合/成员信息，但未形成稳定的查询绑定。

## 能推出与不能推出

可以推出：

1. 在冻结 C1-v1.7 assay 中，rank-8 桥是 value 路径的必要组成；
2. 无差事桥在两个 seed、10k 步内没有学会查询绑定；
3. `payload-only` 同位重建即使自身几乎满分，也不足以教会查询绑定；
4. “通信需要差事”必须加限定：差事还要瞄准真正的绑定/寻址瓶颈。

不能推出：

1. 桥、低秩通信或 Twin 架构一般无效；
2. B/C 永远不会在更长窗口逃逸；
3. 所有重建、预测编码或误差回授差事都无效；
4. rank 8 是带宽瓶颈。本炉没有做 rank sweep，且桥已经足以搬运值集合。

## 下一步建议：把差事从“搬值”改为“按查询绑定”

不建议立刻扫 rank。当前失败形状更像目标错配，而非带宽不足。最小下一炉应保持
同一 C1 考场和 A/B/C-zero 纪律，只把 C 的 job 换成 query-conditioned job：

1. 左支先从 A 事实得到 queried code；
2. 通过左→右桥把 queried code 送给只见 B 事实的右支；
3. 右支在 query/answer 位置预测对应 value；
4. 再由右→左桥把 value 信息送回左支的正式答案头。

这会直接训练缺失的 `code -> value` 绑定，同时仍要求双向桥完成两跳。先做
autograd/可见性/桥清零 smoke 与 Oracle 阳性对照；若两层同步顺序不足以完成
query shuttle，再把“同步次数”作为单独结构变量，而不是与 rank、量化或完整
预测编码闭环一次混改。
