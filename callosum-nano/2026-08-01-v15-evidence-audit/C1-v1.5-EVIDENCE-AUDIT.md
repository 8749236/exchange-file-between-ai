# C1-v1.5 证据审计：结构归因暂停，v1.6 暂不冻结

日期：2026-08-01

## 当前有效判词

K3 执行的 v1.5 五格 endpoint 与配置均有效，pytest 35/35，五格在 step 2000
均未达到逃逸门。除此之外，不再作结构归因：

> 现有证据不能区分“64 IDs 所需预算超过 2000 步”与“Callosum harness 的
> 结构/优化动力学不同”。A/B/C 继续冻结；原计划 v1.6 LONG 暂不冻结。

MATCH 的 value leg 在 2000 步处仍为随机水平，这是保留诊断，不解释为接线
故障或结构病理。

## K3 勘误后的二次审计

K3 主动撤回“64 IDs 在 2000 步必然相变、所以预算无罪”，这个撤回是必要的。
但随勘误附带的复现包还存在三个阻塞问题。

### 1. `verify_n16.py` 实际没有设置 N=16

脚本调用：

```python
g.run('N16', 37, False, steps=2000, B=64, seed=1)
```

被调用的 `repro_grid3.py` 将 `NID = 64` 写死，并在 names、codes、values
生成中全部使用 `NID`。虽另有 `N16 = 16` 常量，但从未被读取。因此归档中的
`n16_their_fmt_2k` 从附带源码看仍是 N=64，不能证明旧曲线来自 N=16。

### 2. 两条声称同源的轨迹不可复现

`verify_n16.py` 与 `map_n64_transition.py` 都调用同一个 `g.run`，参数同为
filler 37、fixed order、batch 64、seed 1；除目标总步数 2000/10000 外，前
2000 步本应完全相同。但两份 JSON 在 step 200 起已经不同，并在 step 1200
分别表现为 `free_c=1.0` 与 `free_c=0.25`。

这可能来自未归档的源码变更、运行环境/线程非确定性，或结果标签问题。查明前
不能用其中任何一条为 20k 窗口定标。

### 3. 猫盆 reference generator 不是 C1Stream 的精确复刻

| 语义 | C1Stream | `repro_grid3.py` |
| --- | --- | --- |
| codes / values | episode 内无重复（`randperm`） | 有放回采样（`randrange`） |
| B facts | 随机 permutation | 与 A facts 同顺序 |
| validation | 固定 1024 | 每次新采 200 |

因此 n64@10k 的“code 在约 5800 步逃逸”是有价值的参考模型观察，但不是本
assay 的直接预算标尺。

## v1.5 归档的 JSONL 故障

endpoint、`result.json` 与 checkpoints 完整；逐步曲线仍发生共享挂载写坏：

| cell | valid curve records | malformed/NUL | missing steps |
| --- | ---: | ---: | ---: |
| BASE | 1985 | 7 | 15 |
| WD0 | 1978 | 8 | 22 |
| W64H2 | 2000 | 0 | 0 |
| ABS | 1956 | 18 | 44 |
| MATCH | 1891 | 7 | 109 |

五个 `metrics.jsonl` 又都缺 step 1。故 v0.1.8 的 append fallback 只消除了崩溃，
没有根治数据稀疏洞。

v0.1.9 改为：训练 step 先在内存形成 ledger，只在 eval/checkpoint 边界把完整
JSONL 写到临时文件、`fsync`，再 `os.replace`；收炉时强制检查本次新产生的
所有 step，无 NUL、无 malformed、无 duplicate、无 missing 才能生成成功结果。
续训时旧的坏记录会被清洗，旧缺口诚实保留；新段必须完整。

## 解冻 v1.6 前的最小复核

1. 修正 reference generator：`id_count` 必须是显式参数，并真正控制采样与
   输出类别；另设 exact-C1 模式（unique code/value、B permutation）。
2. 固定一份脚本 SHA、PyTorch/CPU/thread 配置；同脚本同 seed 连跑两次，先
   验证前 2000 步轨迹能否复现。
3. 分别跑明确标注的 N=16 与 N=64，并附 config 与原始轨迹；validation 至少
   固定 1024，避免 200 样本噪声主导相变边界。
4. v0.1.9 先做短 smoke，确认 `logging_audit.json` 全绿。

完成这些对账后，再在“续训 BASE/MATCH 到 10k 或 20k”之间冻结选择。v1.6
设计通道在此之前保持开放。
